# 저장소 명명 규칙

English: [REPO-NAMING.md](./REPO-NAMING.md)

## 형태

```
<product>-<component>[-<qualifier>]
```

소문자. 단어 사이는 하이픈. 그 밖의 것은 없습니다.

```
careerchat-jobs-api
secondoffice-dashboard
redrob-console
seers-api
```

`<product>` 는 회사가 아니라 제품 계열입니다. 이 조직은 여러 제품 계열을 갖고 있어서 회사 접두어는
아무것도 말해 주지 않습니다. 242개 저장소 전부에서 같기 때문입니다. 두 저장소를 구별해 주는 것은
제품입니다.

`<component>` 는 표면이나 서비스입니다. `web`, `api`, `mobile`, `android`, `ios`, `admin`,
`dashboard`, `landing`, `contracts`, `infra`. 같은 뜻의 다른 낱말보다 이 중 하나를 쓰십시오.
그래야 같은 개념에 `api` 와 `backend` 가 동시에 존재하지 않습니다.

`<qualifier>` 는 한 제품에 같은 컴포넌트가 둘 이상일 때 좁혀 줍니다.
`careerchat-recruiters-web` 과 `careerchat-jobs-web` 처럼.

## 형제 조직

[github.com/redrob-labs](https://github.com/redrob-labs) 도 우리 것이고, 그곳 저장소는 의도적으로
다르게 생겼습니다. `redrob-code`, `redrob-cowork`, `redrob-office`. 거기서는 제품 계열이 Redrob
자체이고 저장소 하나가 제품 하나이므로, 형태는 컴포넌트 토큰이 없는 `redrob-<product>` 입니다.
그 제품들이 웹 계층과 API 계층으로 나뉘지 않고 하나의 애플리케이션으로 출하되기 때문입니다.

두 형태는 같은 규칙입니다. `<product>-<component>` 이고, 산출물이 하나인 제품에는 이름 붙일
컴포넌트가 없는 것입니다. 대칭으로 보이게 하려고 `-app` 이나 `-desktop` 을 붙이지 말고, 그곳에서
`redrob-` 접두어를 떼지도 마십시오. 그 조직에서 그것은 회사 접두어가 아니라 제품 계열입니다.

## 규칙

**컴포넌트를 뒤에 둡니다.** `api-careerchat-jobs` 가 아니라 `careerchat-jobs-api` 입니다. 그러면
알파벳 정렬이 제품을 한데 묶고, 242줄짜리 목록을 실제로 읽는 방식이 그것입니다. 오늘 측정한 값:
91개가 컴포넌트 토큰으로 끝나고, 15개는 그렇지 않은데 전부 한 계열입니다(`redrob-ai-ms-*`,
`redrob-ai-ui-*`, `redrob-ms-mail`, `redrob-ui-mail`). 이 규칙이 문서에 적힌 이유가 그 15개이고,
그것들은 선례가 아니라 유예된 것입니다.

**소문자, 하이픈, 숫자.** 이름은 `^[a-z0-9]+(-[a-z0-9]+)*$` 에 맞아야 합니다. 기존 저장소 12개가
그렇지 않고, 각 형태는 실제 비용을 냅니다.

| 형태 | 현재 예 | 비용 |
|---|---|---|
| 밑줄 | `jobs_scraper`, `redrob_ats_gaurav` | 정렬이 갈라지고 이름을 추측할 수 없게 됩니다. 아무도 밑줄을 첫 시도에 치지 않습니다. |
| 대문자 | `Translack`, `ShortconV2` | git은 대소문자를 구분하고 macOS는 하지 않으므로, 클론이 원격과 달라질 수 있습니다. |
| 점 | `careerchat.me`, `redrob.io` | 호스트명으로 읽히고, 점은 패키지 이름, 모듈 경로, DNS에서 의미를 갖습니다. |

**사람 이름을 넣지 않습니다.** `redrob-ats-shreeti`, `redrob-hrms-tamil`,
`redrob_ats_gaurav` 는 그때 작업하던 사람을 이름에 넣었습니다. 사람은 떠나고 이름은 남아 적극적으로
오해를 만듭니다. 꼭 필요하면 브랜치를 사람 이름으로 하십시오. 저장소는 절대 안 됩니다.

**이름에 버전을 넣지 않습니다.** `ShortconV2` 는 개명 없이는 v3가 될 수 없고, 개명은 비쌉니다
(아래). 버전은 태그와 릴리스에 있습니다. 그것을 위해 만들어진 장치입니다.

**`-new`, `-old`, `-poc`, `-test`, `-demo`, `-copy`, `-final` 을 쓰지 않습니다.** 이것들은 한
순간을 서술하고, 순간은 지나가는데 이름은 남습니다. `devops-poc` 과 `marvel-demo-api` 는 둘 다
아직 여기 있습니다. 저장소가 정말로 임시라면 설명에 그렇게 적고, 끝나면 아카이브하십시오.
`-old` 에는 정당한 용도가 정확히 하나 있고, 아래에 적혀 있습니다.

**공개 저장소의 비공개 짝에는 `-internal` 을 붙입니다.** 오픈소스 저장소를 발행하고 출하할 수 없는
부분을 위해 비공개 트리를 남기는 경우, 비공개 쪽이 `-internal` 을 가집니다. 한정어가 기능이 아니라
가시성을 서술하는 유일한 경우이고, 그럴 자격이 있습니다. 이름을 읽는 사람은 push하기 전에 그것을
알아야 합니다.

**출하되는 이름과 일치시킵니다.** 슬러그와 사용자가 보는 제품명이 일치해야 합니다. `beaver` 라는
저장소가 "Redrob Data" 라고 적힌 문자열을 출하하면, 어느 방향으로든 검색이 실패합니다. 공개한
다음이 아니라 공개하기 전에 개명하십시오.

## 설명과 토픽

이름만으로는 241개 목록에서 저장소를 찾을 수 없습니다. 하나를 찾을 수 있게 만드는 것은 설명과
토픽이고, 둘 다 필수입니다.

**모든 저장소에 설명이 있습니다.** 한 문장, 현재형으로, 그것이 무엇이고 누구를 위한 것인지 말합니다.
제품 이름으로 시작하십시오. GitHub가 저장소 이름 없이 설명만 보여줄 때도 문장이 성립해야 합니다.

```
Redrob Query is a JVM-free, AI-native desktop database client for PostgreSQL, MySQL, SQLite, and MongoDB.
```

120자 아래로 유지하십시오. GitHub는 훨씬 더 긴 것도 받지만, 긴 설명은 조직 목록과 검색 결과에서
잘리고, 그곳이 바로 설명이 도와야 할 자리입니다. 저장소 이름을 그 저장소의 설명으로 쓰지 말고,
자리표시자를 남기지 마십시오. 빈 설명과 `TODO` 는 같은 비용이고, 둘 중 하나는 의도적으로 보입니다.

**모든 저장소에 토픽이 최소 세 개 있습니다.** 다음 축에서 네 개에서 열두 개를 목표로 하십시오.

| 축 | 예 |
|---|---|
| 제품 계열 | `redrob`, `careerchat`, `secondoffice` |
| 컴포넌트 | `desktop-app`, `browser-extension`, `cli`, `microservices` |
| 도메인 | `graphics-editor`, `sql-client`, `identity-verification`, `evaluation` |
| 주 언어와 런타임 | `rust`, `typescript`, `python`, `tauri`, `nextjs`, `electron` |
| 특징 | `local-first`, `self-hosted`, `open-weights`, `i18n`, `korean` |

토픽은 소문자와 하이픈입니다. GitHub가 강제하므로 형태는 선택 사항이 아닙니다. 이름을 그대로 반복하는
토픽(`redrob-query` 에 `redrob-query`)은 넣지 말고, 충실해 보이려고 개수를 채우지 마십시오. 토픽은
클릭되기 위해 존재합니다.

**포크는 상류를 토픽으로 밝힙니다.** `opencode-fork`, `openwork`, `openpencil`, `freecad`,
`chromium`. 포크를 믿을지 판단하는 사람은 코드를 한 줄 읽기 전에 무엇을 포크했는지 알고 싶어 하고,
가장 먼저 보는 곳이 여기입니다.

**배포된 URL이 있으면 homepage를 설정하십시오.** 설명 옆에 렌더링되어 README를 한 번 거치는 수고를
없앱니다.

### 현재 상태

격차는 작지 않고, 한쪽으로 쏠려 있습니다.

| 조직 | 저장소 | 규칙 미달 |
|---|---|---|
| `redrob-labs` | 17 | 0 |
| `mckinley-and-rice` | 241 | 237 |

`redrob-labs` 가 완비된 것은 공개이고 누군가 알아채기 때문입니다. 이 조직은 대부분 비공개라 아무도
알아채지 않았습니다. 79%가 설명이 아예 없고 87%가 토픽이 없습니다.

### 검사

GitHub에는 두 필드를 요구하는 설정이 없으므로, 이 규칙에는 자체 검사가 필요합니다.

```bash
./scripts/audit-metadata.sh mckinley-and-rice        # 보고
./scripts/audit-metadata.sh redrob-labs --fail       # 하나라도 빠지면 비정상 종료
```

규칙이 다루는 그 두 필드를 읽고, 아카이브된 저장소는 건너뛰고, `--fail` 이 있을 때만 실패합니다.
그래서 백로그가 남아 있는 동안에는 보고만 하고, 백로그가 해소되면 게이트로 쓸 수 있습니다. 검사가
강제하는 임계값은 설명 20자 이상, 토픽 3개 이상입니다.

저장소 하나를 고치는 것은 명령 한 줄입니다.

```bash
gh repo edit <owner>/<name> \
  --description "One sentence saying what it is and who it is for." \
  --homepage "https://example.com" \
  --add-topic typescript --add-topic desktop-app --add-topic korean
```

## 개명은 비싸고, 일부는 되돌릴 수 없습니다

GitHub는 옛 이름을 새 이름으로 리다이렉트하지만, 그 리다이렉트는 너무 늦게 알기 쉬운 방식으로
취약합니다.

- **새 저장소가 리다이렉트보다 우선합니다.** 옛 이름 자리에 다른 것이 생기는 순간 리다이렉트가
  끊깁니다. 그래서 아직 옛 이름을 참조하는 것이 하나라도 있다면, 그 이름은 영구히 재사용할 수
  없습니다.
- **액션은 리다이렉트를 아예 따르지 않습니다.** `uses: org/name@ref` 를 쓴 워크플로는 개명 즉시
  깨지고, 구해 줄 리다이렉트가 없습니다.
- **릴리스는 따라오지 않습니다.** 발행된 저장소에 남으므로, 저장소를 개명하는 대신 대체하면 모든
  릴리스 다운로드 링크가 깨집니다.
- **브랜치 보호와 룰셋은 저장소별이고** 손으로 다시 만듭니다.
- **`ghcr.io/<org>/<name>` 패키지는 처음 발행한 저장소에 묶이고, 그 연결은 개명을 따라오지
  않습니다.** 개명 후 새 저장소는 워크플로 권한이 무엇이든 push와 pull 둘 다
  `permission_denied: read_package` 로 거부됩니다. 대신 `ghcr.io/${{ github.repository }}/<name>`
  으로 발행하십시오. 저장소 소유이고 개명을 견딥니다.

그래서, **첫 push 전에 이름을 정하십시오.** 개명이 불가피하다면 아무것도 잃지 않는 순서는
이렇습니다.

1. 기존 저장소를 `<name>-old` 로 개명합니다.
2. **모든 로컬 클론의 remote와 모든 워크플로 참조를 `-old` 로 명시적으로 재지정합니다.**
   여기가 위험 구간입니다. 이 단계를 놓치면 기존 클론의 다음 push가 원래 이름 자리에 지금 있는
   무엇에게로 조용히 갑니다.
3. 비워진 이름으로 대체 저장소를 만들거나 개명합니다.
4. 브랜치 보호와 룰셋을 다시 만듭니다.
5. 컨테이너 이미지를 새 저장소 아래로 다시 발행합니다.

## 가시성

저장소는 기본이 비공개이고, **현재 트리가 아니라 전체 이력**을 감사한 뒤에 의도적으로 공개합니다.
공개 전환은 사실상 되돌릴 수 없습니다. 공개인 동안 만들어진 포크는 별도 네트워크로 살아남고,
포크 네트워크에 들어간 커밋은 브랜치를 지운 뒤에도 상류에서 계속 접근됩니다.

포크는 만들어지는 순간 공개이고, 포크의 가시성은 바꿀 수 없습니다. 공개 저장소의 포크를 위한
비공개 준비 공간이라는 것은 존재하지 않습니다.

## 아카이브

삭제하지 말고 아카이브하십시오. 저장소를 지우면 이슈, 풀 리퀘스트 논의, 태그가 함께 사라지고,
그것들이 보통 어떤 일을 왜 그렇게 했는지에 대한 유일한 기록입니다. 무엇을 지우기 전에, 거기에만
존재하는 것이 무엇인지 먼저 말하십시오.
