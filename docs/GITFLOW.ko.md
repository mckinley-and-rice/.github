# Gitflow

English: [GITFLOW.md](./GITFLOW.md)

오래 사는 브랜치 두 개, `develop` 에서 떼는 짧은 작업 브랜치, 그리고 리뷰를 거친 풀 리퀘스트로
`main` 에 승격되는 릴리스입니다. 이 문서는 설명이고, 게이트는 각 저장소의
`.github/workflows/gitflow.yml` 입니다.

## 브랜치

| 브랜치 | 무엇인지 |
|---|---|
| `develop` | **기본.** 통합. 모든 기능, 수정, 상류 싱크가 먼저 여기로 들어옵니다. |
| `main` | 릴리스된 상태. `develop` 에서 오는 릴리스 풀 리퀘스트로만 전진합니다. |
| `<type>/<slug>` | 하나의 변경. `develop` 을 향한 풀 리퀘스트로 엽니다. |
| `sync/upstream-<tag>` | 상류 흡수. `develop` 을 향한 풀 리퀘스트. 포크에만 있습니다. |
| `hotfix/<slug>` | 이미 릴리스된 것의 수정. `main` 으로, **그 다음** `develop` 으로. |
| `release/<version>` | `develop` 이 계속 움직이는 동안 릴리스를 안정화해야 할 때만. 보통 건너뜁니다. |

`develop` 이 기본 브랜치인 것은 의도입니다. 아무도 대상을 다시 지정하지 않아도 풀 리퀘스트가
그곳을 향하고, 저장소의 기본 브랜치를 읽는 사람은 기여자입니다. 최종 사용자는 릴리스 산출물을
설치하며, 클론하지 않습니다.

`master` 는 쓰지 않습니다.

**기본 브랜치를 바꾸는 것은 CI에 대한 브레이킹 체인지입니다.** `branches: [main]` 로 필터된
워크플로는 기본이 `develop` 으로 옮겨가는 순간 조용히 돌기를 멈추고, 침묵은 실패가 아니므로
아무것도 보고하지 않습니다. 어떤 저장소에서는 그 이유로 `typecheck` 가 풀 리퀘스트에서 0회
실행됐고, 테스트 캐시가 매번 cold miss였습니다. 기본 브랜치를 바꾼 뒤에는 같은 변경 안에서 모든
워크플로의 브랜치 필터를 전수 점검하십시오.

## 작업 브랜치

`<type>/<short-slug>` 입니다. 타입 목록은 **저장소마다** 다르고, 그 저장소의 `ALLOWED_TYPES` 에
있습니다. 목록은 실제로 서로 다르며, 검사는 추측을 실패시킵니다.

| 타입 세트 | 쓰는 저장소 |
|---|---|
| `feat fix chore docs test refactor perf` 에 해당하는 경우 `sync hotfix release` 추가 | 대부분 |
| `feature fix release hotfix` | 오래된 저장소, 그리고 상류 어휘를 따르는 포크 |

브랜치 이름을 정하기 전에 `ALLOWED_TYPES` 를 읽으십시오. 새 저장소는 첫 번째 세트를 씁니다.

브랜치 이름은 변경이 무엇인지를 말하며, 누가 또는 무엇이 만들었는지는 말하지 않습니다. 에이전트나
도구 이름은 타입이 아닙니다.

검사가 이미 실패한 뒤에 브랜치 이름만 바꾸는 것으로는 부족합니다. 실패한 실행은 커밋에 묶여
있으므로 커밋도 함께 amend해야 합니다. 그러지 않으면 새 풀 리퀘스트가 스스로를 머지 가능이라고
보고하면서 옛 빨간 X를 그대로 보여줍니다.

## 머지

| 상황 | 방식 |
|---|---|
| 작업 브랜치를 `develop` 으로 | **squash** |
| 상류 싱크를 `develop` 으로 | **merge 커밋** |
| `develop` 을 `main` 으로 승격 | **merge 커밋** |
| 핫픽스를 `main` 으로 | **merge 커밋** |

상류 싱크를 squash하면 merge base가 파괴되고, 다음 싱크가 이미 가져온 작업을 다시 재생합니다.
승격을 squash하면 같은 관계를 잃습니다. 둘 다 rebase 머지를 절대 쓰지 않습니다.

## 릴리스

버전은 우리 것입니다. `v<major>.<minor>.<patch>`, `0.1.0` 에서 시작합니다. 포크의 버전은 그것이
올라간 상류 버전에서 파생되지 않습니다. 그것은 따로(예를 들어 `UPSTREAM_VERSION` 파일에)
기록하고 릴리스 노트가 그것을 읽어, 릴리스가 무엇에 기반했는지는 여전히 밝혀집니다.

포크 세대를 prerelease 접미사로 인코딩하지 마십시오. `-redrob.N` 접미사는 모든 릴리스를 semver
prerelease로 만들고, prerelease는 자기가 앞서는 릴리스보다 **아래로** 정렬됩니다.

순서는 이렇습니다.

1. 승격 풀 리퀘스트로 `develop` 을 `main` 에 머지합니다.
2. `main` 에 태그를 달고 그 태그에서 빌드합니다.
3. 발행합니다.

순서가 중요하고, 검사됩니다. 승격이 들어오기 전에 `origin/main` HEAD에 태그를 다는 릴리스
워크플로는 새 버전 번호로 **이전** 상태를 출하합니다. 릴리스 경로는 `develop` 이 `main` 보다
앞서 있는 동안 거부하고, 해당 커밋들을 열거하고, 정당한 한 가지 경우(이미 `main` 에 있는 핫픽스)를
위한 명시적 override를 제공해야 합니다.

`main` 은 자동 푸시가 아니라 리뷰된 풀 리퀘스트로 움직입니다. 사람들이 릴리스됐다고 믿는 것이
`main` 이고, 리뷰 없는 푸시를 알아채기 어려운 유일한 브랜치가 `main` 입니다.

릴리스에 서명이 붙는 경우, 먼저 `dry_run` 으로 한 번 돌리십시오. 빌드, 서명, 공증까지 하고 아무것도
발행하지 않으며, 서명 자격증명이 이 저장소에서 실제로 보이는지 확인하는 유일하게 확실한 방법입니다.
조직 시크릿은 이름으로 상속되고 admin 없이는 목록을 볼 수 없으므로, API의 `403` 은 읽을 수 없다는
뜻이지 없다는 뜻이 아닙니다.

빌드 하나를 통째로 날린 릴리스 기계 두 가지.

**릴리스 잡에 git 신원을 주십시오.** `git tag -a` 는 tagger를 기록하므로, `user.name` 과
`user.email` 이 없는 bare 러너는 empty ident 오류로 죽습니다. 빌드, 서명, 공증이 모두 성공한
다음의 마지막 단계에서 그렇습니다.

**자산은 하나씩, 재시도와 함께 업로드하십시오.** assets glob을 쓴 `gh release create` 는
원자적입니다. 자산 20개 중 하나에서 일시적 `5xx` 하나가 나면 릴리스 전체가 롤백되고 40분짜리
실행이 버려집니다. 릴리스를 빈 상태로 만들고, 각 자산을 backoff와 함께 올린 뒤, 발행된 개수가
빌드된 개수와 같은지 단정하십시오.

릴리스를 멱등하게 만드십시오. 태그가 한 번 생기면 그것을 만들려는 재시도는 실패하고, 그 버전은
영구히 쓸 수 없게 됩니다. 기존 태그를 재사용하고 기존 릴리스를 편집하십시오.

## 핫픽스

`develop` 이 아니라 `main` 에서 브랜치를 뗍니다. 수정이 릴리스되지 않은 작업을 끌고 오지 않게 하기
위해서입니다. `main` 을 향해 풀 리퀘스트를 열고, 거기서 릴리스한 뒤, **`main` 을 `develop` 으로
되머지합니다.** 그러지 않으면 다음 릴리스에서 수정이 사라집니다.

이 마지막 단계가 실제로 건너뛰어지는 단계이므로 검사합니다. `main` 에 푸시가 있을 때마다
`gitflow` 워크플로는 `main` 이 `develop` 에 없는 커밋을 갖고 있는 동안 실패하고 그 커밋들을
열거합니다. 언제든 직접 읽을 수 있는 불변식은 이것입니다.

```bash
git rev-list --count origin/develop..origin/main   # 릴리스 구간 밖에서는 0
```

어떤 저장소에서 이 값이 한 달 동안 0이 아니었습니다. `bun install --frozen-lockfile` 수정이
`main` 에 들어갔고, 되머지가 끝내 일어나지 않아, 기본 브랜치가 자기 `packageManager` 가 핀한
bun 버전으로 설치되지 않았습니다. 위 규칙은 이미 적혀 있었습니다. 아무것도 검사하지 않았고,
아무것도 검사하지 않는 규칙은 취향입니다.

## 상류 싱크(포크)

상류의 개발 브랜치가 아니라 **태그**를 따릅니다. 태그는 상류 자신이 일관되다고 판단한 지점입니다.

```sh
# 한 번
git remote add upstream <upstream-url>

# 매 싱크
git fetch upstream --tags
git switch develop && git pull
git switch -c sync/upstream-<tag>
git merge <tag>
```

풀 리퀘스트는 `develop` 을 향해 엽니다. 상류를 `main` 에 곧바로 머지하지 않습니다.

우리가 실제로 돌린 모든 싱크에서 성립한 세 가지.

- **merge base가 실재하므로 상류의 대부분은 공짜로 들어옵니다.** 3-way 머지는 우리가 건드리지
  않은 모든 파일에 대해 상류 버전을 취합니다. 진짜 이견만 해결하면 됩니다.
- **충돌은 리브랜딩에 몰립니다.** 상류가 우리가 개명한 줄을 편집한 곳에서는 머지가 어느 쪽이
  이기는지 알 수 없습니다. 우리 것을 유지하고, 그들의 주변 변경을 취합니다.
- **일부 상류 식별자는 기능을 지고 있습니다.** 충돌을 해결하는 도중에 리브랜딩을 마무리하지
  마십시오. 레거시 설정 디렉터리 이름은 기존 설치가 계속 동작하도록 의도적으로 읽히고, 오류
  코드는 클라이언트가 문자열 비교로 분기하는 계약이며, 일부 패키지 이름은 우리가 개명할 권리가
  없는 실제 발행 패키지입니다.

## CI가 강제하는 것과 강제할 수 없는 것

`.github/workflows/gitflow.yml` 은 두 트리거에서 두 잡을 돌립니다. 서로 다른 순간에 서로 다른
질문에 답하기 때문입니다. 브랜치 이름은 풀 리퀘스트가 생긴 뒤에만 판정할 수 있고, 되머지 누락은
`main` 이 움직인 뒤에만 판정할 수 있습니다.

저장소가 필수 체크에 넣지 않는 한 두 잡은 차단하지 않고 보고만 합니다.

풀 리퀘스트 트리거에 브랜치 필터를 걸지 마십시오. 기본 브랜치를 빠뜨린 필터는 조용히 돌기를
멈추고, 그것이 이 워크플로가 부분적으로는 잡으려고 쓰인 실패입니다.

**워크플로는 풀 리퀘스트를 열 수 없고, 그 권한을 줘서도 안 됩니다.** 워크플로에서
`gh pr create` 는 조직 설정을 켜기 전까지 `GitHub Actions is not permitted to create or approve
pull requests` 로 실패하고, 그 하나의 설정이 생성과 승인을 함께 허용합니다. 공개 저장소에서 풀
리퀘스트를 승인할 수 있는 워크플로는 자기 것을 승인할 수 있습니다. 끄고 두십시오. 워크플로가
브랜치를 push하고 run summary에 compare URL을 적게 한 뒤, 사람이 풀 리퀘스트를 열게 합니다.

그 실패를 `|| echo 'already open'` 으로 삼키지 마십시오. 하드 실패를 양성 상태로 보고하고, 다른
모든 원인까지 감춥니다.

## 브랜치 보호

`develop` 과 `main` 을 보호하십시오. 모든 것이 풀 리퀘스트로 들어오고, force push와 삭제는
막습니다.

필수 체크는 풀 리퀘스트에서 실제로 도는 체크여야 합니다. `workflow_dispatch` 전용 워크플로를
필수로 걸면 모든 풀 리퀘스트가 영원히 기다립니다. 그러니 멈춰 둔 테스트 스위트는 필수 체크가 될 수
없습니다. 필수로 걸고 왜 아무것도 머지되지 않는지 의아해하는 대신, 그 사실을
`CONTRIBUTING.md` 에 적으십시오.

브랜치 보호는 저장소별이고 이 저장소에서 **상속되지 않습니다.** 개명되거나 새로 포크된 저장소는
보호 없이 시작하며, 룰셋을 다시 만들어야 합니다.
